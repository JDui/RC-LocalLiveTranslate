# 本地翻译提速规划与本轮界面调整

初始记录：2026-10-12，界面、字号、记录命名已实现，当时翻译部分仅规划现有 Hy-MT2 STQ 的优化。现行线程策略见下面的 2026-10-23 更新。根据所有者要求，模型替换暂缓，不执行 OPUS、ML Kit 或其他后端接入；未测量真实手机提速。

## 2026-10-23：允许更高的翻译资源占用

根据所有者“允许翻译模型有更高的性能占用以提升效率”，默认“自动”模式启用按可用 CPU 核数决定的线程预算。令 `C = max(1, Runtime.availableProcessors())`，`B = min(C, max(2, C - 2))`；生成线程为 `min(B, 4)`，预填充线程为 `min(B, 6)`。例如 8 核为生成 4 / 预填充 6，6 核为 4 / 4，4 核与 2 核仍为 2 / 2，单核为 1 / 1。这是初始资源策略，未证明是各手机的最佳组合；预留并发余量不等于绑核或独占物理 CPU。

省电或 MODERATE 热状态将后续语段降至最多 2 / 2，严重压力仍暂停翻译，临界压力仍停止采集。恢复沿用 30 秒稳定窗口。在翻译 worker 内、每句生成前按最新策略配置线程；JNI 配置与生成、释放共用同一 mutex，切换预算复用已有 context，不重新加载权重。正在执行的同步句子完成后才应用新预算，监测线程不操作 native context。

保留单翻译 worker、容量 8 的有界队列、1024 context、768 prompt / 256 output token、EOG 完成检查和 60 秒 abort。模型、量化、提示、greedy、许可、CPU 后端和采集路径均不变。下面列出的预加载、KV 前缀缓存、逐步显示、短句与 GPU/NPU 优化仍为规划。构建和策略回归不能代替真机提速、温度、内存或 ASR 同时运行验收，结果见 [验证记录](11_VALIDATION.md)。

## 已落实的截图要求

- Live 顶部只保留语言选择；去掉大标题、翻译图标、麦克风/演示分段切换和模型状态行。
- 双语开关留在设置；演示入口移到设置，运行/暂停时锁定，Live 始终保留演示标记。
- 模型数量及安装状态放到模型导航入口。展开屏侧栏下方显示数量，普通字号的底栏合并到模型标签；大系统字体使用短标签，状态仍可由无障碍语义读取。
- 录音状态、计时、停止、开始/暂停/继续合为一行；缩小外边距、导航宽度和导航留白，触控目标仍至少 48 dp。
- 字幕减少上下留白、原译文间距、分隔线间距，以字号比例设置行高；完整 final 不再重复显示“已确认”，识别中、修订、翻译中、不可用仍保留。
- 平展屏的字幕列表占用导航之外的完整宽度；真实分隔/遮挡铰链仍沿用安全分区及译文伴随区，不跨铰链。
- 字号范围为 8–24 sp，滑块步长 1，设置读写都限幅；旧 25–28 设置读取为 24。双语的较小原文字号至少 8 sp，保留系统字体缩放。

## 对话记录命名

新麦克风及演示记录的默认名称为 `yyyy-MM-dd-HH:mm-[city]`，例如 `2026-10-12-23:26-[上海]`。使用日历年 `yyyy`，不使用容易在年末跨年的周历年 `YYYY`。

日期、分钟和城市在会话开始时固定，不使用停止/导出时间；暂停恢复不改名。城市来自设置中的“记录城市”，离线手动填写，留空为 `[未设置]`。不请求定位权限，不用时区、语言或 SIM 卡推断城市。名称中保存开始时的设备本地时间，因此新记录在切换系统时区后不会变名。

旧数据库不需破坏性迁移：原始 `createdAt` 和字幕保留，两个旧默认名称“本地对话”“多语言对话 · 演示”在列表及详情按同一格式显示，城市为未设置；旧记录未保存原时区，只能按当前设备时区展示。自定义名称保留，重命名功能继续可用。导出建议文件名沿用显示名称，将 Windows 不允许的冒号替换为短横线；TXT/SRT/JSON 格式不变。

## 2026-10-12 基线中已确认的等待来源

| 来源 | 当时代码 | 对体验的影响 |
| --- | --- | --- |
| CPU 与线程 | `hy_jni.cpp`：`n_gpu_layers=0`，生成和预填充都固定 2 线程 | 没有利用手机 GPU/NPU；2 线程是否最佳未知，需与 ASR 同时运行测量 |
| ARM 内核构建 | 项目 CMake 固定 `GGML_NATIVE=OFF`、`GGML_CPU_ALL_VARIANTS=OFF`，未显式设置 `GGML_CPU_ARM_ARCH`；固定 STQ ARM 源码有 DOTPROD 路径与基础 NEON 仿真路径 | 优先核查实际编译宏/指令，不能仅凭 ARM64 ABI 认定用了最佳内核 |
| 首段加载 | `HyTranslator` 首次翻译才创建模型及 context | 第一条翻译包含冷启动；后续 handle 复用，不能把每句慢都归因于加载 |
| 输出发布 | JNI 输出到 EOG 才一次性返回 | 用户在整句生成完成前看不到译文，首字延迟与整句延迟相同 |
| 排队 | `RealtimePipeline` 单翻译 worker、FIFO 容量 8 | 持续说话时慢任务会积累；减小队列不等于加快模型 |
| 输入与输出 | 每段清空 KV，上限 768 prompt tokens / 256 output tokens，60 秒 CPU abort | 重算固定指令；长段耗时更大。token 上限是上限，不意味着每句一定生成 256 tokens |
| 解码 | 已经 greedy | 改成温度 0 或“关闭 beam”不能再次消除已经不存在的采样/beam 开销 |

ASR/VAD/说话人不在本轮替换范围。录音线程继续与推理隔离。现有 `RunDiagnostics` 已有各翻译方向耗时、队列等待和队列统计；先导出同一手机上的公开句子诊断，确认冷启动、排队、模型计算各自的占比。

## 保留模型的优化优先级

| 优化 | 实际加速还是显示改善 | 质量影响 | 优先级 |
| --- | --- | --- | --- |
| 分开测冷启动、prefill、decode、排队、UI发布 | 先定位；不直接加速 | 无 | P0，先测 |
| 核查并评测 DOTPROD 原生内核 | 可能缩短实际计算；当前是否启用要从编译与二进制确认 | 量化权重不变；做内核数值和六向回归 | P0，优先于线程扩展 |
| 对照生成和预填充的 2/3/4 线程 | 可能缩短计算；要同时测 ASR 2线程及 speaker 1线程的争用 | 同一提示和 greedy 通常不主动降低质量，但仍做数值回归 | P0 |
| 在语音首段前预加载同一模型 | 缩短第一句等待；热句计算不变 | 无 | P0 |
| 保留固定指令 KV 前缀 | 少重算指令；完整源句仍需 prefill，短前缀收益可能有限 | 不携带前句正文时可保持语段隔离 | P1 |
| 逐步发布译文 | 提前看到首字；完整生成耗时不因此变短 | 临时结果必须清楚标记，EOG 后才完整 | P1 |
| 有界等待、过期段不再翻译 | 降低实时队列延迟；不加速单句 | 牺牲部分积压语段的翻译覆盖，原文保留 | P1，显式快速模式 |
| 自然语义边界分段 | 降低一段等待、生成长度和阻塞 | 日语句末信息、指代、否定可能受影响 | P2，质量回归后 |
| GPU/NPU | 取决于固定 STQ 内核及硬件支持 | 不应通过不兼容权重强行开启 | P2，先核查，暂不执行 |

当前已经是 greedy 和 1.25-bit STQ，不把温度改零、再“关闭 beam”或继续压缩权重当作确定的新收益。腾讯在 Apple A15 上公布 1.25-bit 相比传统 4-bit 的约 1.5 倍速度，只能作为该测试的说明，不能代表 Android 手机表现。

## 推荐执行顺序

### 第一轮：保留当前模型，先拆解等待

1. 使用同一批公开短句测冷启动和热启动，按中日/中英/英日六向记录翻译计算与排队的 p50/p95、句长、输出 token 数；不记录用户私密文本。
2. 检查实际 APK 内 `librc_hymt.so` 的构建日志、`compile_commands.json`、ARM 编译宏和反汇编。固定 upstream 的 `ggml_vec_dot_stq1_0_q8_K` 在 `__ARM_FEATURE_DOTPROD` 存在时使用原生 `vdotq_s32`，否则基础 NEON 模拟点积。项目未设置 ARM 架构且关闭变体，是需要验证的优化机会，不是“已证实旧 APK 没有 dotprod”。先做兼容内核与 `armv8.2-a+dotprod` 隔离构建对照；上线必须有 CPU 特征检测和旧设备回退，不全局强加指令。
3. 对比 2/3/4 线程的生成及预填充组合，测试 ASR 同时运行及持续 30 分钟。按 p95、温度、ASR丢段选择，不能全开线程挤占拾音/识别。
4. 录音启动时由翻译 worker 预加载，在首段识别前尽可能完成；单实例、模型租约和取消/释放不变。预热只消除冷启动，独立报告热句结果。
5. 缓存固定指令前缀的 KV、保留每段边界隔离，禁止携带上段私密正文；源/目标语言变化、超时或错误时失效缓存。按完整提示 tokenization 后的公共 token 前缀确认边界，不按 UTF-8 字符或字节数切 KV，以免边界合并改变 token。基线回归比较提示模板和翻译质量。
6. 增加明确的翻译 partial 状态，以 UTF-8 完整字符、约 80–120 ms 合并发送逐步结果。只在 EOG 后标完整，截断/超时不可发布为完整译文；停止和修订丢弃过期回调。当前 reducer 的 `translationRevision` 会拒绝同一 revision 的第二次结果，不能直接反复发送同 revision 的现有 Translation 事件；需要保持 ASR revision 绑定，并额外定义单次生成的 chunk 序号与 final 结束标记，旧 JSON 字段继续兼容。
7. 快速模式设有界的等待期限和较小队列，例如最多 2 段等待、等待超过 1.5 秒的段保留原文并明确标“未翻译（积压）”。这些是待验证初值，不能静默丢字幕，也不默认改动完整历史模式。
8. 在自然标点/稳定语义边界切短句，先测 32/64 source tokens 档；日语句末关系、否定、数字及专有名词特别检查。不按字符硬截断，不把语段截断误当完整翻译。

### 暂缓项

模型替换、标准 Q4 权重、OPUS-MT、ML Kit、NLLB、直接中日蒸馏全部暂缓。先按上面的无换模顺序建立手机数据；不为此修改模型身份门禁、导入协议、权重许可证或联网权限。

STQ 是自定义量化，`n_gpu_layers=0` 不能直接改为全卸载就宣称 GPU 生效。当前固定 llama.cpp PR 的 ARM CPU 内核、编译 ISA 和发布脚本也应检查：区分手机支持的指令与实际构建启用的指令，ARM64 优化必须在 CPU 兼容检查之后启用，不能导致其他设备非法指令崩溃。

原规划将线程实验放在隔离基准或开发选项中；2026-10-23 所有者已授权提高默认资源预算，采用上面的有上限自适应策略。仍不默认全核，不放宽输出完成校验，不用截断译文伪装加速。会话启停、模型租约、60秒 abort 与非取消资源释放回归必须保留。

## 验收与退出条件

- 翻译环节目标：10–30 个汉字量级或相当长度的公开短句，热运行六向 p95 ≤ 1.5 秒；端到端目标 2–4 秒。均为目标，并非本轮结果。
- 分别计量语音段结束→ASR final、ASR final→翻译入队、排队→生成开始、模型首输出、完整输出、UI 发布；流式首字不得混称整句耗时。
- 每方向至少 50 个普通会话句，额外各含否定、数字/时间、专有名词和口语省略；先保证含义、数字和否定不反转，再判断是否接受流畅度下降。
- 断网首次启动和重复启动都验证；30 分钟测试队列、内存、热状态、拾音/识别丢段；省电和严重压力降级回归。
- 若现有模型优化后仍达不到目标，保留原文优先降级并明确记录瓶颈与未达标方向；是否再考虑换模由所有者后续决定，不自动执行。
